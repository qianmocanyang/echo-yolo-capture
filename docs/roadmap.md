# 后续可做的事：优化清单与 YOLO 训练集成

> 写于 2026-09-14，基于 v1.3.0 的代码实况。每条都标了**依据**（实测数字或代码位置），
> 不是"感觉可以优化"的清单。

---

## 〇、一句话结论

- **优化点**：性能上只剩「图片库翻页」一处用户能明显感觉到的卡顿（实测 239ms）；
  其余更值得做的是**数据一致性体检**和**工程基建**（UI 测试、类型检查、体积瘦身）。
- **训练集成**：技术上完全可行，但**不能内嵌**——卡在许可证、体积、硬件三道关。
  可行形态是「echo 做环境编排 + 训练在独立进程里跑」，分两步走。

---

## 一、优化清单

### 1.1 性能（有实测数据，改动收益最直接）

| # | 问题 | 依据 | 改法 |
| --- | --- | --- | --- |
| **P1** | 图片库**翻页时同步解码 96 张缩略图**，主线程阻塞 | 实测 320×320 PNG ×96：**冷缓存 239ms**、热缓存 10ms | 后台线程预解码成 `QImage`（可跨线程），主线程只做 `QPixmap.fromImage`。占用格子先显示灰色占位 |
| **P2** | 缩略图缓存 `lru_cache(512)`，图库超过 512 张后**翻页反复 miss** | `echo/ui/imaging.py` | 容量提到 2048，或改成按「当前页 ±1 页」的显式 LRU（翻回上一页必然命中） |
| **P3** | 一页构造 **96 个 widget**（每个 = QWidget + QLabel + QCheckBox） | `library_page.py: PAGE_SIZE = 96` | 降到 48；或改 `QListView` + 自定义 delegate（一个控件画全部格子） |

> P1 是唯一一处**目前用户还能感觉到**的卡顿（上一轮的采集侧 CPU 已从 97.8% 降到 3~15%）。
> 239ms 正好是"翻一下要顿一下"的量级。

### 1.2 数据一致性（比性能更值得做）

现在写入顺序是「先原子落盘 → 再插数据库」（`pipeline.py:1048 / 1085`），顺序是对的；
SQLite 也开了 WAL + `integrity_check`。**缺的是"发现并修复不一致"的工具**：

| # | 问题 | 说明 |
| --- | --- | --- |
| **D1** | **库体检**（建议优先）：扫描三类不一致 | ① **孤儿文件**：磁盘上有 PNG、数据库没记录（换过保存目录、导入了外部图）；② **幽灵记录**：数据库有记录、文件已不在（**上一轮回收站报错 124 的根因土壤**）；③ **零字节/损坏 PNG**。给出一键"清孤儿 / 清幽灵" |
| **D2** | 数据库损坏时的自动降级 | `integrity_check` 已有但不清楚损坏后是否自动备份重建。建议：检测到损坏 → 重命名成 `db.corrupt-<时间>.sqlite` → 建新库 → 提示重新索引图片目录 |
| **D3** | 保存目录被移动/改名后无引导 | 现在只会显示"无法预览"。体检功能可顺带给出"目录已失效，请重新指定" |

## 二、YOLO 训练集成

### 2.1 三道硬约束（先看这个，再谈方案）

**① 许可证：Ultralytics 是 AGPL-3.0，echo 是 MIT**

Ultralytics 官方 FAQ 把「**Scripts for training, validation, and inference**」明确列进
"需要以 AGPL-3.0 开源的衍生作品"范围里。所以：

- ❌ 在 echo 主程序里 `import ultralytics` → 这一部分必须 AGPL（强 copyleft 会蔓延）
- ⚠️ 通过 subprocess 调 `yolo` CLI → 属于「独立程序聚合」（GPLv3/AGPLv3 第 5 条），
  边界相对安全，但"进程间通信紧密集成"在法律实践上仍有争议，**必须在文档里明示**
- ✅ echo 只**生成**训练脚本 / 命令交给用户，用户在自己环境里装 ultralytics →
  分发的是 echo 自己的模板代码，不是 ultralytics，风险最低

**② 工程：打包版没有 Python 解释器**

`dist/echo/` 里只有 `python313.dll`，**没有 `python.exe`**（已实测确认）。
PyInstaller 打出来的 exe 不能当通用解释器用，所以 **echo 无法"顺便"运行训练脚本**，
必须依赖外部 Python 环境（系统 Python / uv / conda）。

顺带一个数字：把 `torch` + CUDA 打进去，包体从 **236MB → 1.5GB+**。
为了训练功能把所有采集用户拖到 1.5GB，不划算。

**③ 硬件：训练要独显**

| 配置 | YOLO11n / 640px / 100 epochs / 1000 张 |
| --- | --- |
| RTX 3060 级 | 约 10~20 分钟 |
| 纯 CPU（Ryzen 5 5600H 级） | **约 5~10 小时**（基本不现实） |

显存需求约 2~4GB（batch=16 @ 640px）。**采集用户里大量是核显笔记本**——
这说明训练入口必须先探测硬件，跑不动就直说，而不是让用户点了等一晚上。

### 2.2 三个方案

| | T1 训练脚手架 | T2 训练控制台 | T3 换 Apache 系框架 |
| --- | --- | --- | --- |
| **做什么** | 导出数据集时，往导出目录写 `train.py` + `train.bat` + `requirements.txt`，用户在导出目录双击 bat 自己跑 | echo 探测系统 Python → 引导建独立 venv → subprocess 启动训练 → 实时解析 stdout 显示进度 → 支持中断/续训 → 训练完自动 `export onnx` | 改用 YOLOX / MMDetection / PaddleDetection / 原版 RT-DETR（均 Apache-2.0） |
| **许可风险** | 最低（种子脚本是 echo 原创，只调第三方 CLI） | 低-中（进程隔离，需文档明示） | 无 |
| **工程成本** | 小（1~2 天） | 中（1~2 周） | 大（生态弱、数据集格式要新写一套转换） |
| **用户体验** | 要离开 GUI 用命令行 | 全在 GUI 内，进度可视 | 同 T2 但工具链粗糙 |
| **维护成本** | 低 | 中（要跟 ultralytics 版本变化） | 高 |
| **推荐** | ✅ 先做 | ✅ 后做 | ❌ 除非必须闭源商用 |

### 2.3 推荐路线

```
第一步（T1）  导出目录里生成训练脚手架，让流程能跑通、验证数据集质量
      ↓
第二步（T2）  把这一步搬进 GUI：环境探测 → 建 venv → 起训练 → 进度可视化
      ↓
第三步（F1）  训练产物 onnx 回灌 echo：预标注 + 效果验证，闭环完成
```

**关键点：训练集成的价值不在"能训练"，而在"闭环"。** 完整链条是

```
采集 → 标注 → 导出 → 训练 → 导出 onnx → 回灌 echo 做预标注/验证 → 补采 → 再训练
```

后半段（onnx 回灌）正是 `docs/auto-label-research.md` 里的路线 C。
**建议把「训练集成」和「onnx 推理」放在同一个版本里规划**，只做前半段等于只做了一半。

### 2.4 T2 的接口设计要点（真要动手时看）

- **解释器探测顺序**：`sys.executable`（源码运行时）→ `py -0p`（py launcher，本机可用）
  → `where python` → 都没有就引导去装。打包版走第 2 条起。
- **环境隔离**：`python -m venv <导出目录>/.train-env`，不污染用户全局环境。
  装 `ultralytics` 时明确提示会下载 **约 2.5GB（CUDA 版 torch）**。
- **硬件探测**：调 `nvidia-smi` 拿显卡型号与显存，据此给出**预计耗时**再让用户点开始。
- **进度解析**：训练日志是逐行输出的，正则抓 `^\s+(\d+)/(\d+)` 这类 epoch 行 + `mAP50`。
  不要用 `torch`/`ultralytics` 的 Python API 拿进度——那会打破进程隔离。
- **中断处理**：向子进程发 Ctrl+C（`CREATE_NEW_PROCESS_GROUP` + `send_signal`），
  ultralytics 会保存 `last.pt`，续训用 `resume=True`。
- **产物归档**：训练结束把 `best.pt` / `results.csv` / `confusion_matrix.png`
  拷到导出目录的 `runs/`，onnx 存到 `<保存目录>/models/` 供 echo 推理用。

## 三、优先级汇总

| 优先级 | 项 | 理由 |
| --- | --- | --- |
| **P0** | D1 库体检 | 直接解决"记录与文件对不上"这一整类 bug 的根源（回收站 124 只是它的一个症状） |
| **P0** | P1 + P2 图片库翻页 | 唯一一处用户还能明显感觉到的卡顿，实测 239ms |
| **P1** | E1 + E2 UI 测试与静态检查 | 这几轮 bug 全在 UI 层，却只有 smoke 脚本能测。不补基建，下轮还会踩 |
| **P1** | T1 训练脚手架 | 成本小、立刻让"采集→训练"闭环能跑通，也是 T2 的中间态 |
| **P2** | F1 + T2 onnx 回灌与训练控制台 | 真正的产品价值所在，但要等数据集和流程验证过 |
| **P2** | E4 + E5 体积瘦身与签名 | 面向"分发给朋友"这个真实场景 |
| **P3** | F2/F3 内置标注与预标注 | 大工程，且要先有 F1 的推理能力打底 |
| **P3** | U1~U4 / F5~F7 体验项 | 锦上添花 |

## 四、明确不建议做的

| 想法 | 为什么不做 |
| --- | --- |
| 把 torch / ultralytics 内嵌进 echo.exe | 包体 236MB→1.5GB+，且 AGPL 会蔓延到整个项目 |
| echo 里做云端训练 | 用户群是单机游戏玩家，数据是本地游戏截图（含版权内容），上传云端不合适 |
| 为了规避 AGPL 而自己重写训练框架 | 训练框架的坑以年计，重写成本远超换许可证的收益 |
| 用 YOLO-World 做零样本预标注 | GPL-3.0，同样传染。要零样本就按调研文档走 Grounding DINO（Apache-2.0） |
